# Архитектура

## Границы

`web` и `server` — независимые npm-приложения с собственными package.json/lockfile,
Dockerfile, TypeScript и ESLint. Общих runtime-пакетов, workspace и ORM нет.
Взаимодействие — REST `/api`; API-типы определены локально в обеих частях.
Основной Compose содержит три сервиса: web, server и db (каталог метаданных).
`compose.samples.yaml` — отдельный локальный стек из PostgreSQL, MySQL и MongoDB для примеров.

## Backend

- `database/`: пул pg служебной БД, транзакции и runner SQL-миграций.
- `modules/auth/`: email OTP, Resend, access/refresh JWT, глобальный guard и пользователи.
- `modules/connections/`: DTO, REST-контроллер, бизнес-сервис, SQL-репозиторий, шифрование.
- `modules/connections/connectors/`: общий контракт Connector и отдельные PostgreSQL,
  MySQL, MongoDB адаптеры на pg/mysql2/mongodb.
- `modules/databases/`: совместимый общий каталог и дополнительный JSON-импорт.
- `modules/health/`: доступность приложения и служебного PostgreSQL.

Контроллер валидирует запрос. ConnectionsService выбирает адаптер, получает/шифрует секрет
и организует синхронизацию. Адаптер знает только внешний движок и возвращает нейтральный
Catalog/DataPage. ConnectionsRepository знает только служебные таблицы и вручную написанный
SQL. Он не обращается к удалённой БД. SecretsService отвечает за AES-GCM.

Подключение — сохранённый профиль, а не бессрочно открытый сокет. Для проверки, синхронизации,
страницы данных и SQL-запроса создаётся короткая нативная сессия, закрываемая в finally. Пул удалённых
соединений и постоянные фоновые соединения пока не нужны; пул pg относится только к каталогу.

Все рабочие REST-маршруты проходят через глобальный Bearer guard; публичны только health,
отправка/проверка OTP и refresh. UUID пользователя передаётся в сервисы из проверенного JWT.

Создание: проверка доступности и авторизации внешней БД → сохранение профиля владельца и зашифрованного секрета →
синхронизация. Если авторизация неверна, профиль не создаётся. Если соединение проверено,
но синхронизация не удалась, профиль остаётся в error для повторной попытки.

## Frontend / FSD

- `app`: маршрутизатор, Redux store, глобальные токены и тема.
- `pages`: каталог, страница выбранной БД и SQL workspace.
- `widgets`: shell и обозреватель объектов.
- `features`: подключение, DataGrid, Monaco SQL editor, таблица результатов, JSON-импорт и удаление.
- `features/auth`: RTK Query email OTP, auth slice и локальная сессия.
- `pages/sign-in`: двухшаговый экран email → код.
- `entities/database`: типизированные RTK Query endpoints и карточка каталога.
- `shared`: REST-база, локальные контракты, форматирование, UI и выбор темы.

RTK Query добавляет access JWT к запросам, хранит серверное состояние, инвалидирует каталог после создания, удаления
и обновления структуры. DataGrid читает live page по connectionId + objectId + offset/limit.
При смене объекта новый key сбрасывает пагинацию. Доступны данные, структура, индексы,
ограничения. SQL workspace выполняет запрос через отдельную RTK Query mutation; черновик
хранится в localStorage отдельно для каждого connectionId.

## Каталог и live data

GET /databases объединяет подключения с офлайн-снимками; source определяет сценарий.
Для подключения schemas собираются из нормализованной активной версии. Для JSON-снимка
schemas берутся из прежнего JSONB. Сервер принимает objectId для чтения, разрешает его
только внутри текущего каталога этого подключения и сам экранирует имя объекта.
Для обычного просмотра пользователь передаёт только objectId. Произвольный SQL принимается
только маршрутом query для сохранённого PostgreSQL/MySQL-подключения. MongoDB pipeline не
принимается. SQL-запрос и результат не участвуют в каталоге метаданных.
